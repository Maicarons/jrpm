| `outgoing_queue` (إعادة التوجيه عبر الشبكة) | طبقة شبكة jrpm مختلفة (OutgoingCommandPacket/ServerNetworkGameSocketHandler::SendCommand) | إعادة تشغيل عبر الشبكة تحتاج إلى إعادة كتابة منطق إعادة التوجيه 🟠 |

| تنسيق الملف | خاص (معرف أمر vanilla + تدفق بتات) | معرف أمر jrpm يختلف تماماً عن vanilla ← ملفات إعادة التشغيل غير متوافقة، **يحتاج التنسيق إلى إعادة تصميم** 🟠 |

## رابعاً: المسار العام الموصى به

```
① نظام التمييز (أساس الدفعة الثالثة، ~2-3 جولات)      ← أساس عرض المخططات/التقسيم
② طبقة كائن الأوامر (أساس مخططات الدفعة الثالثة + إعادة تشغيل الدفعة الخامسة، ~1-2 جولة)
③ المخططات (~1 جولة)
④ تقسيم المدن (~1.5 جولة، يعتمد على ① خط أنابيب العرض؛ growth_tiles باستخدام بوابة XSLF)
⑤ إعادة تشغيل الأوامر + التصدير (~2 جولة، يعتمد على ②؛ يمكن تصدير JSON بشكل مستقل مسبقاً)
⑥ أوامر خادم CM (تُدرج متفرقة بين الدفعات، gamespeed/step يمكن القيام بهما فوراً)
```

## خامساً: العناصر التي يمكن تنفيذها فوراً بتكلفة منخفضة (لا تعتمد على أي مشروع كبير)

1. أمر `cmgamespeed` (~20 سطراً، تغيير `_game_speed`)
2. `step` موجود بالفعل ← لا حاجة للتنفيذ
3. `cmgamestats` / `cmgfxdebug` (كل ~1 ساعة، مستقل)
4. تصدير JSON لـ `cmexport` (~2 ساعة، مستقل)
5. `cmtreemap` (~2 ساعة، مستقل)

هذه العناصر الخمسة حوالي **نصف يوم عمل**، يمكن تنفيذها كـ "دفعة صفرية" أولاً، بالتوازي مع الدفعات الثالثة/الرابعة/الخامسة دون تعارض.
